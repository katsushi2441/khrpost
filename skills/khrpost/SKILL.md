# khrpost — 職務・目標・引継ぎ管理の設置・運用スキル

khrpost は「職（ポジション）」を主役にした職務・職責・目標・タスクの管理。
1ファイルPHP + SQLite。レンタルサーバーに置くだけで動く。常駐プロセスもDBサーバーも要らない。

## ファイル構成（触っていい場所）

| ファイル | 役割 | 編集 |
|---|---|---|
| `khrpost_config.php` | パスワード・社員マスタの場所・等級表 | **設定変更はここだけ** |
| `khrpost.php` | 本体（全画面・全処理） | 改造時のみ |
| `khrpost_data/khrpost.sqlite` | 職・任命・職務・タスクの台帳 | **直接編集禁止** |
| `khrpost_data/employees.json` | 社員マスタ（置く場合） | 人事側の都合で更新 |

## 設置の手順

1. `khrpost.php` と `khrpost_assets/` をサーバーに置く
2. `khrpost_config.php.example` を `khrpost_config.php` にコピーする
3. パスワードを決める。`KHP_PASSWORD`（管理者）と `KHP_STAFF_PASSWORD`（担当者共通）
   - 本番は `KHP_PASSWORD_HASH` を推奨: `php -r "echo password_hash('パスワード', PASSWORD_DEFAULT);"`
4. **社員マスタを用意する**（下記。ここを飛ばすと動かない）
5. ブラウザで `khrpost.php` を開く。管理者ログイン → 職を作る → 任命する

`khrpost_data/` には `Deny from all` の `.htaccess` が自動生成されるが、
**公開ディレクトリの外に置けるなら `KHP_DATA_DIR` でそちらを指すほうが良い**。

## 社員マスタは khrpost の外にある（最重要）

khrpost は社員を持たない。誰が在籍しているかは会社の情報であって、
職の管理システムが二重に抱えると必ずズレる（退職者が残る・氏名が食い違う）。

`KHP_EMPLOYEES_DIR` に、`employees.json` があるディレクトリを指定する。

```json
{"employees":[
  {"id":"e1","no":"E001","name":"山田 太郎","status":"active"},
  {"id":"e2","no":"E002","name":"佐藤 花子","status":"active"}
]}
```

| キー | 意味 |
|---|---|
| `id` | 社員を一意に識別する文字列。任命と記録者がこれで紐づく。**運用開始後に変えない** |
| `no` | 社員コード。担当者ログインのID |
| `name` | 氏名 |
| `status` | `active` 以外はログインできない |

### 「社員を追加して」と頼まれたとき

**khrpost 側では追加できない。** マスタ元を直す。

- kvgwc を使っているなら → kvgwc の社員画面で追加する（`KHP_EMPLOYEES_DIR` は kvgwc_data を指しているはず）
- 自前のJSONなら → `employees.json` に1行足す。`id` は他とかぶらない新しい文字列にする

### 「退職者を消して」と頼まれたとき

**消さない。** `status` を `retired` に変えるだけにする。
マスタから消すと、その人が残したタスクの記録者名が「（マスタにない社員）」になる。
消したいのは在籍情報であって、過去の記録ではない。

### 既存の人事台帳・CSVから employees.json を作る

CSVを読んで上の形式で書き出す小さなスクリプトを書けばよい。`id` は社員番号を
そのまま使ってもよいが、**社員番号が変わりうる運用なら別の不変IDにする**。

## よくある依頼と正しいやり方

### 「等級の基準を変えて」
`khrpost_config.php` の `KHP_GRADE_TABLE` を編集する。
```php
define('KHP_GRADE_TABLE', 'S:120,A:105,B:90,C:75');  // この値以上ならその等級。下回ればD
```

### 「達成率が120%で頭打ちになるのをやめて」
`KHP_RATE_CAP` を上げる。`999` にすれば実質無制限。
```php
define('KHP_RATE_CAP', 999);
```
ただし上限を外すと、1つの目標を大量にこなした職のスコアが不当に高くなる。既定の120%は
「頑張りは認めるが、他の目標を放置した分は取り返せない」という設計。

### 「職を追加したい」「必要人数を変えたい」
管理画面から行う。ホーム → 職を登録。設定ファイルは触らない。

### 「実績の数え方を変えたい」
実績＝タスクのうち「やったこと」が書かれている件数。これは `khp_duty_actual()` 1か所で
計算している。金額や件数の合計にしたいなら、tasks に数値列を足してこの関数を直す。
**画面のあちこちで数え直さないこと**（ズレる）。

### 「担当者が他人の職も見られるようにしたい」
`khp_assert_post()` が「その職の担当者本人か」を見ている。ここを緩める判断は慎重に。
閲覧だけ許すなら、書き込み系のアクションだけ従来どおり弾くようにする。

### 「権限を増やしたい」
`khp_can($actor, $action)` の `$rules` に足す。**画面側で権限判定を書かない。**
関門が1か所であることが、この製品の安全性の根拠。

## 壊してはいけない設計

1. **社員マスタを khrpost に持たせない** — 二重管理は必ずズレる
2. **達成率をAIに計算させない** — `khp_rate()` が決定的に計算する。人事の数字は再現できることが要件
3. **タスクは職（post_id）に紐づける** — 人に紐づけると、担当者が代わった瞬間に履歴が消える。
   前任の記録を後任が読めることが、この製品の存在理由
4. **権限判定は `khp_can()` の1か所** — 画面に散らすと必ず漏れる
5. **登録フォームのタブ（これまでの記録からコピー）を消さない** — 入力が面倒だと誰も使わなくなる

## 動作確認

```bash
php scripts/check_khrpost.php     # 自己テスト65項目。改造したら必ず通す
```

このテストには「構造の単純さ」の機械チェックが入っている（テーブルが4つを超えない、
社員テーブルを作らない、画面が5つを超えない等）。落ちたら、機能を足すより先に
**本当にその複雑さが要るのか**を疑うこと。

## 仕様の要点

- PHP 7.0以降 / `pdo_sqlite`
- テーブルは4つ: `posts`（職）/ `assignments`（任命）/ `duties`（職務・職責・目標）/ `tasks`
- 職務・職責・目標は 1:1:1 なので1行に3つ持つ
- 達成率 = 実績 ÷ 目標値（上限 `KHP_RATE_CAP`）／ 職スコア = 目標の達成率の単純平均
